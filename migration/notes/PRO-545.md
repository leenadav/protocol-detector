`tools/check_security_requirements.py` kept only lines matching its ROW regex, so a row whose last cell was free text ("manual review"), had prose after the closing backtick or lacked a cell was dropped with rc=0, and nothing noticed a duplicate or deleted id; `main` already had SR-58..SR-63 twice (the presentation/key-log rows and the RDP, database, SNMPv3, Kerberos, cipher-suite and server-name rows). The gate now treats every table row whose first cell starts with `SR` as a requirement row and fails when it does not parse as `| SR-n | requirement | `refs` |` (no leading zeros), on an empty or malformed reference item, on a duplicate id, and when the id set differs from the new `tools/security_requirements.lock.json` (deleted row, unpinned new row, reused retired id). `--write-lock` pins the ids and refuses to drop one unless it is named with `--retire`. The six newer duplicates are renumbered SR-70..SR-75 (no other file referenced them; `docs/PROGRESS-V065.md` names the older SR-58..SR-63). The tool gains `--self-test` (17 cases), run by `make requirements`. Out of scope: SEC-PYRM-2 (Python references grepped rather than run) and SEC-PYRM-4 (Go test outcome parsing). Follow-up (SEC-PYRM-10, P3): the row filter still needed a leading `|` and an ASCII `SR`, so `SR-76 | ... | manual review |` or a row with a Cyrillic `Ѕ` was never parsed and gave rc 0. Now every line holding `|` must be the header, a separator or a strict row (ASCII id, `[ \t]` spacing), and a pipe-less line starting with an id-like token after NFKC fails too; self-test 27 cases.
